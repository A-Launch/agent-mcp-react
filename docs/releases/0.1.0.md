# `@agent-mcp/react` 0.1.0

> *Dated material.* `§` numbers and references to the project's internal principles below refer
> to the development record this release was built against, which is maintained outside this
> repository; the current design is in [design.md](../design.md). The public `v0.1.0` tag marks
> where this release was published, on a tree later than the release itself; the exact release
> tree is not in this repository's history.

The first release. It implements §50's minimum viable release in full, and **two things it
deliberately does not claim are stated below** — read those before quoting the rest.

## What it is

A browser-side React library that exposes a running React application as an MCP server, so an agent
can drive the application through typed tools instead of clicking its UI.

**MCP is a second control interface onto one application** — not browser automation, and not a second
store. Both the human UI and the agent act through the same application state transitions.

## What ships

**Level 1 — application control.** `useMcpTool` declares a tool from the component that owns the
feature; `useMcpState` publishes state for an agent to read back. Tools appear on mount and leave on
unmount, and a handler always sees current state. `registerMcpTool` declares one from outside React —
a shell, a router, a singleton service — and adapters bind Redux, Zustand and router actions on top.

**Level 2 — semantic DOM control. Experimental.** `dom.snapshot`, `dom.get_text`, `dom.click`,
`dom.fill`, `dom.select`, `dom.press`, `dom.scroll`. Roles and accessible names, never page HTML. A
fallback for flows nobody instrumented — *a DOM tool for a flow that already has an application tool
is a regression, not a convenience.*

**Level 3 — JavaScript execution.** `runtime.evaluate`, behind four conditions: import the subpath,
grant the capability, wire a confirmation resolver, and have a person approve each call.

**The capability model.** Three levels, structurally separated: a module, a capability and a subpath
export each. One level confers nothing on another. `application: true` does not make a DOM tool
callable, `dom.inspect` does not imply `dom.interact`, and nothing short of `evaluate` reaches Level 3.

**Never registered.** No Level 2 or Level 3 tool enters `document.modelContext` in any configuration,
including one that granted it — verified in Chromium, Firefox and WebKit.

**The transport.** An authenticated WebSocket the browser dials outbound, with a fresh credential per
attempt, reconnection on a documented backoff, and one MCP message per frame.

## Measured, not asserted

| §44 clause | Measured against the built artifact |
|---|---|
| under 50 KB gzip, initial runtime overhead | **27.0 KB** main entry (35.9 KB all nine exports) |
| 500 tools remain functional | 500 registered, all listed, the last one callable |
| no polling when idle | **0** frames across an idle interval on a live connection |
| invocation overhead under 5 ms | **0.34 ms**/call — an upper bound, including the socket round trip |

Reproduce with `node scripts/measure-bundle.mjs` and `pnpm test:transport`.

Also measured: a build that does not import `@agent-mcp/react/dom` is **7,691 bytes smaller** and
contains none of it; one that does not import `/evaluate` is **1,982 bytes smaller**. Granting a
capability puts nothing in a bundle.

## A known limitation you must read before deploying

**The bundled validator requires CSP `unsafe-eval`.** `createAjvValidator` — the one the documentation
recommends and the demonstrator uses — compiles schemas with `new Function`. Under a `script-src` that
omits `unsafe-eval` it throws while compiling, and this library refuses to register a tool whose
declared schema has no working validator. **A strict-CSP application therefore exposes no tools at
all.**

Measured in a real browser; recorded in
[docs/issues/validator-requires-unsafe-eval.md](../issues/validator-requires-unsafe-eval.md).

**The workaround is the seam working as designed:** `SchemaValidator` is an interface the application
supplies, so a strict-CSP deployment brings a validator that compiles nothing.
`examples/customer-dashboard/src/csp-safe-validator.ts` is a worked example — deliberately minimal, and
explicit about which keywords it covers.

It is not fixed in `0.1.0` because fixing it means shipping a second validator or precompiling schemas
at build time, both of which are new scope. What was wrong was that **no document said so**, and that
is now corrected everywhere the validator is mentioned.

## What this release does NOT claim

**§45's browser matrix is a support _target_, not verified support.** The suite ran on Playwright's
Chromium 151.0.7922.34, Firefox 153.0 and WebKit 26.5 — 13 cases each, all six required APIs present.
Playwright's Chromium is not Chrome or Edge, its WebKit is not Safari, and none can be pinned to
"current and previous 2". Twelve real-browser runs would close it; they have not been done.
[docs/browser-support.md](../browser-support.md) carries the checklist.

**Level 2 is experimental**, per §50's own permission. Its reference staleness is derived at use time
and includes a witness of the role and accessible name a snapshot published — which catches a DOM node
React recycled into different data, but **cannot tell two identically-named elements apart**. A column
of "Open" buttons is that case.

**Interactability does not cover layout.** An element that is zero-sized, clipped, or covered by an
overlay is interactable to the Level 2 write tools. Detecting otherwise needs layout, and layout is
unreadable in the environment most of this library's tests run in — a check for it would report
success while checking nothing.

**The content-security-policy refusal path is now verified** — it was recorded as inconclusive at
`0.1.0`'s first cut and has since been exercised on all three engines: a page served under a real
policy without `unsafe-eval`, a person approving the call, and `MCP_RUNTIME_EVALUATE_FORBIDDEN` coming
back rather than a syntax cause. Getting there required the seam above, which is how the validator
limitation was found.

## Requirements

- **React**: declared as a peer at `>= 18`, and **verified against 19.2 only**. The declared range is
  a compatibility intent, not a tested one — the same distinction this release makes for browsers, and
  it is stated rather than left for a consumer to discover. If you need 18, test it.
- A secure context — the tool registry is defined only in one; `localhost` counts
- Engine floor, set by `AbortSignal.any`: **Chrome 116, Safari 17.4, Firefox 124**
- **Pack and publish with `pnpm`, not `npm`.** `publishConfig` rewrites the export map to point at
  `dist/`, and npm does not apply `publishConfig` field overrides — packed with npm, every export in
  the tarball points into a `src/` tree the tarball does not contain. `node scripts/verify-package.mjs`
  checks this; it was found by a review, after six green gate commands.

## Not in this release

A production ticket service, multi-tab orchestration policy, rate limiting, a telemetry pipeline, a
Streamable HTTP transport (an explicit non-goal), and CI bundle-size enforcement. Each is deferred by
decision rather than overlooked; the constitution's Proportionate Engineering section names the
substitute for each.


## Licence

**Apache 2.0.** Chosen over MIT for one substantive reason: this library implements a draft browser
standard and an original capability model, and Apache 2.0 carries an **express patent grant** where
MIT leaves the position implicit. Standards-adjacent work is where that distinction stops being
theoretical.

The trade accepted with it: Apache 2.0 is **incompatible with GPLv2** (GPLv3 is fine). Every runtime
dependency is MIT, so nothing upstream constrained the choice.

`LICENSE` and `NOTICE` ship in the package, and the published manifest declares `Apache-2.0`.
