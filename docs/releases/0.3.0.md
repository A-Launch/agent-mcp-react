# `agent-mcp-react` 0.3.0

**A refused declaration no longer unmounts your application.** That is the whole release, and it comes
from a first integration by somebody outside this project, working from the published package.

## What they hit

They forgot to import the validator when adding a second tool. The symptom was not a refused tool — it
was a **blank page**. The library re-threw the refusal from the provider's render, so the console
message naming the exact import to add sat underneath a tree that no longer rendered. A developer who
adds a tool, forgets an import, and sees a white screen has no reason to connect the two.

## Why it changes

The argument for throwing was stated in the code and is a real one: an application cannot log past a
throw, so a setup mistake cannot be ignored. The argument against won.

**MCP is a second control interface onto one application.** That sentence is the first thing this
library's own documentation says about itself, and it settles this: a misconfigured second interface
must not take down the first. A person's UI does not stop working because an agent's did.

The inconsistency made it plainer. Production already left the page standing for a contested name —
its own case says *"a production build that tore a page down because a screen was mounted twice would
be a worse outcome than the collision it is reporting."* Only development threw, which is precisely
where the author is standing.

## What did NOT change

**The declaration is still refused.** The tool is absent from `tools/list`, uncallable by an agent and
by any script on the page. Surviving the refusal does not mean surviving into the registry — a tool
registered with a contract nothing enforces is the state the validation feature exists to end, and a
case asserts the registry stays empty.

## What got better

**The refusal is scoped to the declaration that earned it.** The throw took the whole tree down, so a
page with one unvalidated tool exposed *nothing at all*. Now the other tools stay registered — asserted
over a real socket, where a sibling tool remains in `tools/list` while the unvalidated one is absent.

## What you may need to change

**`McpRegistrationEvent#prefix` is optional.** It only ever meant anything for a reserved-prefix
refusal, and the event now carries every cause. A TypeScript consumer reading `event.prefix` must
handle `undefined`. That is the only source change this release asks for.

If you relied on a refused declaration throwing — to fail a test, or to stop a boot sequence — wire
`onRegistration` and decide for yourself. It fires for every cause with a `code` you can branch on.

## Where refusals go now

| | |
|---|---|
| `onRegistration` | every refused declaration, both builds, with its `code` |
| the console | development only, with the declaration site, for an author who wired no observer |
| `onUnexpectedState` | unchanged — it receives what it received before |
